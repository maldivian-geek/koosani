## [Unreleased]

### Added

- **Order lists: derived "System Item" column** (ARCHITECTURE.md §4.16, FUNCTIONS.md §orderLists/§items). A line's `itemName` is the customer's wording; every line-returning response now also carries `systemItemName` — the catalogue item's name, resolved at read time by a case-insensitive match against `items.customer_item_name` (new read-only `items.findByCustomerItemNames` service lookup; never stored, so it tracks catalogue changes). Shown as a muted read-only column on the detail screen; renaming a line inline re-resolves it from the PATCH response.
- **Order lists: every line field is now editable inline** (`OrderListDetailView.vue`). The lines table uses DataTable `editMode="cell"`: click Item, Qty, UOM, Note, or Additional Note → edit → Enter/click-away PATCHes just that field, with the same optimistic-then-revert-on-error behavior as the status dropdowns. Qty input is validated client-side (thousands separators stripped; non-numeric input reverts with a warning); an emptied UOM falls back to "Each"; an emptied note clears to null; an emptied item name reverts. Requires the `orders.edit` permission — without it the table stays read-only. No API change (`PATCH /order-lists/:id/lines/:lineId` already accepted all fields).
- **Order lists: paste/CSV import with review-and-confirm** (FUNCTIONS.md §orderLists). "Import" on the order-list detail screen accepts rows pasted from Excel (TSV) or CSV — positional columns `Item, Qty, Unit, Note, Additional note`, header row auto-skipped, thousands separators stripped from quantities, non-numeric qty defaulting to 1. The server parses to draft rows (`POST /order-lists/:id/lines/parse`, persists nothing); the user edits/removes rows in a preview table, then confirms (`POST /order-lists/:id/lines/bulk`, max 500 rows, one transaction, single `order_list.import` audit row) — satisfying SECURITY.md §13.13's review-and-confirm requirement for bulk imports. Parsing reuses `papaparse` (already a dependency — no STACK.md change). An AI image-import path (photo of a printed sheet → drafts via Claude vision) is planned as a later phase feeding the same review screen.
- App version shown at the bottom of the web sidebar (`SidebarContent.vue`), injected at build time from `web/package.json`'s version via a Vite `define` (`__APP_VERSION__`, declared in `web/src/env.d.ts`). All workspace `package.json` versions bumped to `1.1.0` and are now kept in lockstep with CHANGELOG releases — bump them as part of the release step (CHANGELOG.md protocol).
- **Phase 34 — Order Lists:** a new lightweight `orderLists` module for named working checklists of stock-order lines, modeled on a spreadsheet the owner already used — see ARCHITECTURE.md §4.16.
  - New `order_lists`/`order_list_lines` tables (migration `0013_phase34_order_lists.sql`) — not a financial document: no GST, no numbering, no stock movement, `item_name` is free text (not linked to the items master, a deliberate product decision). Each line carries independent `payment_status` (`pending`|`paid`) and `stock_status` (`unknown`|`in_stock`|`available`|`not_available`) enums.
  - New routes: `GET/POST /order-lists`, `GET/PATCH/DELETE /order-lists/:id`, `POST /order-lists/:id/lines`, `PATCH/DELETE /order-lists/:id/lines/:lineId` (FUNCTIONS.md §orderLists). Every mutation writes an audit row (`order_list.create`/`.update`/`.delete`/`.line_add`/`.line_update`/`.line_delete`). New `'orders'` `PermissionResource` (SECURITY.md §Authorization Model).
  - Web: a new "Order Lists" sidebar entry (purchases group), a list view, and a detail view where each line's Payment Status and Stock Status are edited inline via `Select` components that PATCH immediately — status colors follow the existing `StatusTag` severity convention (paid → success, not_available → danger, in_stock/available → info, pending/unknown → secondary), not the source spreadsheet's own colors.
- **Items — Customer Item Name (Phase 34):** items gain an optional `customerItemName` field — how a specific customer refers to the item on their own POs/paperwork. Display/reference only; not wired into any PDF or the customer portal (possible follow-up if that's ever needed). Shown in the item create/edit drawer only — the items list columns were already full, so it's not added there.

## [1.1.0] - 2026-08-24

### Added

- **Production containers for api/worker/web** (STACK.md "Infrastructure" §): `docker-compose.prod.yml` + `api/Dockerfile.prod` (multi-stage: compiles TS, runs `node dist/*.js`) + `web/Dockerfile.prod` (multi-stage: `vite build`, served via nginx with SPA fallback routing, `web/nginx.conf`) — for a Coolify-style compose-based deploy, separate from the dev-container setup added earlier. `FILES_STORAGE` defaults to `s3` in this file, overridable to `local` as a stopgap (`local` is dev/test-only — see STACK.md).
  - `@koosani/shared`'s `package.json` gains a `"production"` exports condition pointing at `./dist/*.js` (default remains `./src/*.ts`, unchanged, for `tsx`/Vite) — opted into only via `NODE_OPTIONS=--conditions=production` in the api prod image's runtime stage. Needed because a production Node process can't execute `.ts` directly the way `tsx` does.
  - Every service in `docker-compose.prod.yml` gets a `deploy.resources.limits.memory` cap, and both prod Dockerfiles' build stages cap `NODE_OPTIONS=--max-old-space-size` and pnpm's `--network-concurrency` (STACK.md "Build/runtime resource caps"). A production build on the actual deploy host once spiked hard enough to OOM-kill unrelated processes on the shared server, not just the build itself.
  - `pnpm-workspace.yaml`'s `allowBuilds` blocks `cpu-features` (a native, CPU-heavy accelerator for `ssh2`, itself only pulled in transitively by the `@testcontainers/postgresql` devDependency — never used at runtime) — found as the likely trigger for the above.
  - New `api/src/db/seedProd.ts` + `api/docker-entrypoint.sh`: the `api` service's container entrypoint now runs `drizzle-kit migrate` then the idempotent production seed (env-driven `ADMIN_BUSINESS_NAME`/`ADMIN_EMAIL`/`ADMIN_NAME`, optional `ADMIN_PASSWORD` — a secure one is generated and printed once to logs if unset) before starting the server, so a fresh production database gets a real schema and one admin login without a manual step (STACK.md "Migrations + admin bootstrap"). `worker` (same image) bypasses both via a command-override detection in the entrypoint script. Deliberately separate from the existing `db/seed.ts`, which stays dev/demo-only (fixed business name, fixed known password) and must never run against production (SECURITY.md §13.12).
  - Root `package.json` pins `"packageManager": "pnpm@11.4.0"`; both prod Dockerfiles use `corepack prepare pnpm@11.4.0 --activate` instead of plain `corepack enable` (STACK.md "pnpm version pinning") — the latter meant the `api` prod image's runtime stage lazily fetched pnpm over the network on the container's first cold start.
  - SECURITY.md §13.12 gains a note on exposing the API under the web app's own domain via a path prefix (`/api/*`) instead of a second subdomain, since the browser (not the web container) calls the API directly and CORS is origin- not path-based. The actual prefix-stripping happens at `web`'s nginx layer, not Traefik — see the next entry.
  - `web/nginx.conf` gains a `location /api/` reverse-proxy to `http://api:3000` (STACK.md "Exposing the api under the web app's own domain"), and `api` loses its `docker_compose_domains`/Traefik routing entirely (only `web` is Traefik-routed now, to the whole domain). A first attempt did this purely via Traefik: an explicit router `priority` label on `api`'s `Host && PathPrefix(/api)` router, since Coolify's auto-generated routers for `api` and `web` (`Host && PathPrefix(/)`) had no priority set on either and `web`'s catch-all won by default. That label was verifiably present in the live deployed config but still didn't change the routing outcome, for reasons not fully diagnosable from the Coolify API alone — routing everything through one Traefik router and letting nginx handle the internal split sidesteps the ambiguity entirely instead.

- **Responsive sidebar navigation** (DESIGN.md §11) — below `md`, the sidebar previously just didn't render at all (`hidden md:flex` with no fallback), leaving no way to navigate on a phone except editing the URL directly. New `SidebarContent.vue` extracts the nav content (brand, groups, user/sign-out) into one source rendered twice by a rewritten `SidebarNav.vue`: a PrimeVue `Drawer` overlay below `md` (hamburger-triggered, full labels, auto-closes on navigation), and the existing fixed aside at `md`+ (icon-only at tablet width, full labels again at `lg`, via a `compact` prop toggling `md:hidden lg:block` on each label). `TopBar.vue` gains the hamburger button (mobile only) and a static notification-bell placeholder (no backing feature yet — layout only). `AppLayout.vue` gains a phone-only bottom nav (Dashboard/Invoices/Customers + a "More" button opening the same drawer).
- **`EntityList`'s `DataTable` stacks into labeled cards on mobile** (DESIGN.md §11 "EntityList's DataTable stacks..."). PrimeVue 4 dropped PrimeVue 3's `responsiveLayout="stack"` — `DataTable`'s `breakpoint` prop still exists but isn't wired to anything in this version, so this is done via `pt`: `EntityList.vue`'s `DataTable` hides `thead` and turns each body row into a bordered flex-column card below `md`. New `shared/ui/entityListColumnPt.ts` exports `stackPt`, a per-`<Column>` pass-through that reads the column's own `header` prop and sets `data-label` on its body cell (a CSS `content: attr(data-label)` pseudo-element shows it as a label prefix on mobile only). Applied to all 73 `<Column>` elements across all 14 list views that use `EntityList` (invoices, credit notes, delivery notes, estimates, POs, bills, customers, suppliers, items, users, projects, expenses, recurring invoices, inventory movements).

### Changed

- **Production Postgres moved from an embedded `docker-compose.prod.yml` service to a separate Coolify-managed database resource** (STACK.md "Postgres is a separate Coolify Database resource"). Modeled on the same pattern already used by another Maldivian Geek project (`roanuedhuru_v3`) on the same Coolify instance: `docker-compose.prod.yml` no longer has a `postgres` service or `postgres_data` volume at all; `migrate`/`api`/`worker` join Coolify's own shared `coolify` external Docker network (`networks: coolify: external: true`) and reach the new standalone `postgres:18-alpine` resource by its Coolify resource UUID as hostname (`DB_HOST` env var, new `DB_PASSWORD` alongside it — both set as Coolify env vars, replacing `POSTGRES_PASSWORD`). Gains a Coolify-managed backup/restore UI and direct per-resource logs/terminal access for Postgres specifically; loses the simplicity of one fully self-contained compose stack.
  - New dedicated one-shot `migrate` service (`restart: "no"`, runs `drizzle-kit migrate` then the idempotent production seed, then exits) replaces `api`/`worker` each running migrate+seed on their own container start — both now override their command (`node dist/server.js` / `node dist/worker.js`) to skip straight past `api/docker-entrypoint.sh`'s default flow, and instead `depends_on: migrate: condition: service_completed_successfully` (STACK.md "Migrations + admin bootstrap"). Local dev's `docker-compose.yml` is unchanged — still an embedded `postgres` service, still uses the entrypoint script's default migrate+seed+serve flow.
  - Local dev's `postgres` image bumped `16-alpine` → `18-alpine` (`docker-compose.yml`) to match the new production resource's version. The test suite's `@testcontainers/postgresql` instances (25 files) deliberately stay on `16-alpine` for now — not bumped in this change.

### Fixed

- **Local dev Postgres couldn't start at all under `postgres:18-alpine`** (`docker-compose.yml`): 18+ images require the volume mount at `/var/lib/postgresql` (data in a subdirectory), not the pre-18 `/var/lib/postgresql/data` — the container exited with an explicit refusal on every boot since the 16→18 image bump. Mount corrected, and the service now uses a fresh `postgres18_data` volume; the old `postgres_data` volume holds a pg16-era cluster this image cannot run and is left untouched for manual recovery or deletion (`docker volume rm koosani_postgres_data` once confirmed unneeded).

- **Auth security scan follow-ups** — role change / delete no longer leave a live JWT with stale access, portal session-cache parity, a bogus accept-invite rate limiter, and portal draft-document exposure (SECURITY.md §JWT, §13.2, §Rate Limiting, §13.14).
  - `users.update` bumps `token_version` (inside the existing transaction) when `data.role` is defined and differs from the current role; `users.softDelete` bumps it too, in the same transaction as the soft delete. Both routes (`PATCH /users/:id` when the body includes `role`, `DELETE /users/:id`) call `invalidateSessionCache` after the service call so the in-process 30s session-cache window (SECURITY.md §13.2) doesn't leave a demoted or deleted user's old JWT accepted after the DB-level revocation already happened (FUNCTIONS.md §users).
  - `auth.resetPassword` now returns `{ ok: true; userId }` instead of `{ ok: true }`; `POST /auth/reset-password` uses it to call `invalidateSessionCache(userId)`, closing the same cache-window gap for the reset-password flow (FUNCTIONS.md §auth).
  - `auth/repository.ts`'s `incrementTokenVersion` now accepts either the plain db client or an open transaction (`Db | DbTx`), since it's called from `users/service.ts`'s existing transactions as of the above.
  - Portal must not expose draft documents. `invoicing.listInvoices`/`estimates.listEstimates` (repository + service) gain an optional `excludeDraft` flag; `portal/routes.ts`'s list routes always pass it. Portal detail/pdf/accept/decline routes additionally 404 (same shape as an ownership mismatch — no information leak) when the fetched document's `status === 'draft'` (FUNCTIONS.md §portal, §invoicing, §estimates; SECURITY.md §13.14).

### Security

- **Rate limiters moved to a dedicated fail-fast Redis connection** (`redisRateLimiter` in `api/src/lib/redis.ts` — SECURITY.md §13.7 Implementation). The BullMQ connection's required `maxRetriesPerRequest: null` + ioredis 6's offline queue meant a rate-limiter command issued while Redis was down never rejected — so rate-limiter-flexible's in-memory insurance limiter never engaged and every rate-limited request (login, magic-link, portal auth, exports) hung indefinitely instead of degrading. The dedicated connection (`maxRetriesPerRequest: 2`, `enableOfflineQueue: false`) restores the designed fallback; BullMQ keeps its own infinite-retry connection.

- **`POST /accept-invite` dropped its bogus per-"email" rate limiter.** The second limiter was keyed `invite:${token.slice(0, 8)}` — attacker-controlled (the token, not an email, since the request body has no email field) and of no defensive value against brute force, while actively locking out a legitimate invitee retrying the same link more than 5 times in 15 minutes. Removed; the existing per-IP `strictLimiter` is the real defense (SECURITY.md §Rate Limiting).
- **Portal session cap.** `portalAuth/repository.ts`'s `createSession` now caps active sessions at 10 per `(businessId, customerId)`, evicting the oldest by `lastUsedAt` before insert — mirrors the staff session cap (SECURITY.md §Session Management, §13.14, FUNCTIONS.md §portalAuth).
- **Portal magic-link verify now checks the customer still exists before creating a session.** `portalAuth.verifyMagicLink` calls `customers.assertExists` (the customers service, not its repository — ARCHITECTURE.md §3) immediately after consuming the token, before `issueSession` runs — a customer soft-deleted between token issue and verify no longer gets an orphaned active session (previously also a 500, since the route's own `assertExists` ran only after the session/cookie were already created). The service's success result now carries `{ id, name, email }` directly so the route doesn't need its own follow-up lookup (SECURITY.md §13.14, FUNCTIONS.md §portalAuth).
- **SECURITY.md §IP Detection gains an explicit deployment-requirement paragraph** for `X-Real-IP` trust: `getRealIp()` trusts the header unconditionally, and `web/nginx.conf` forwards the inbound `$http_x_real_ip` rather than setting it from `$remote_addr`, so correctness depends entirely on the Traefik layer not permissively trusting client-supplied forwarded headers and on nothing reaching `web`'s port 80 directly. Doc-only — no code change (SECURITY.md §IP Detection).
- **Dependency security pass (stage 1 of the audit's upgrade path)** — `pnpm audit --prod` is now clean (was 5 high / 16 moderate / 1 low). `hono` 4.12.18 → 4.13.3 (13 advisories, incl. a ReDoS in the CORS middleware this app runs on every request), `drizzle-orm` 0.38.4 → 0.45.2 (SQL-identifier-escaping SQL injection, GHSA-gpj5-g38j-94v9) + `drizzle-kit` 0.31, `@hono/node-server` → 1.19.15 (stayed on 1.x), `vite` → 6.4.3, `vitest` 2 → 3.2 (clears the dev-only UI-server RCE advisory). `pnpm-workspace.yaml` gains per-major `overrides` floors for vulnerable transitives (nanoid, postcss, shell-quote, brace-expansion, undici@6, protobufjs, js-yaml, js-cookie, tmp, @grpc/grpc-js, uuid@11, vite@6) — note: overrides must live in `pnpm-workspace.yaml`, not `package.json` `pnpm.overrides`, to take effect under this pnpm version. Remaining advisories are dev-test-only (`undici@5`/`uuid@10` solely via `@testcontainers/postgresql@10`, cleared by its planned major bump; old `esbuild` lines via build tools).

- **The search icon overlapped the input text/placeholder in every list view's search bar** (`EntityList.vue`, shared by all 14 list views). The manual pattern — an absolutely-positioned icon plus `pl-9` on `<InputText>` to clear it — didn't reliably win against PrimeVue's own theme CSS for the input's padding. Switched to PrimeVue's dedicated `<IconField>`/`<InputIcon>` components (DESIGN.md §11), which coordinate the padding through PrimeVue's own theme system instead.
- **Login (and reset-password/accept-invite) showed no error at all on failure — the page just silently reset.** `apiFetch` treats any `401` response as "session expired" and hard-redirects to `/login` (`window.location.replace`) unless the caller opts out with `noRedirect: true`. But `/auth/login`, `/auth/reset-password`, and `/auth/accept-invite` all use `401` for their own expected failure case (wrong password / invalid or expired token) — none of the three views passed `noRedirect: true`, so a failed attempt triggered a full page reload back to `/login` before any error message could render, wiping the form. `ResetPasswordView.vue`/`AcceptInviteView.vue` additionally checked `err.status === 400` for their "link is invalid or expired" message, but the routes actually return `401` — so even without the redirect, that branch would never have matched. Added `noRedirect: true` to all three `apiFetch` calls and corrected the status check to `401`; `LoginView.vue`'s error-message logic also had a second bug (`status === 422` / `status !== 401` — neither branch matches an actual `401`), simplified to show the fixed "Invalid email or password." string on any failure, matching this repo's auth-error convention (SECURITY.md).
- **The Postgres-resource split (above) briefly took production down.** `migrate`/`api`/`worker`'s `DATABASE_URL` hardcoded `?sslmode=require`, but the new database resource's `enable_ssl` is `false` — the server was never configured to accept SSL connections, so every connection attempt failed, `migrate` exited 1, and `api`/`worker` never started at all (`depends_on: migrate: condition: service_completed_successfully`) — Traefik had nothing to route to (`no available server`). Changed to `sslmode=prefer` (STACK.md "sslmode=prefer, not require — a hard-won lesson").
- **Password reset, invite, and magic-link emails linked to nonexistent frontend paths.** All three (`auth.forgotPassword`, `auth.requestMagicLink`, `users.create`'s invite) built links as `${FRONTEND_URL}/auth/<page>`, but the web app's router (FUNCTIONS.md's frontend doesn't list routes, but see `web/src/router/index.ts`) registers these pages at the bare path (`/reset-password`, `/magic-link`, `/accept-invite`) — no `/auth` prefix. The stray prefix meant every link 404'd (well, silently rendered nothing matching in the SPA — nginx's history-mode fallback still serves `index.html`, so Vue Router just found no route). Fixed the three link-building strings; also added `MagicLinkVerifyView.vue` + its `/magic-link` route, which didn't exist at all before (only the "request a link" form existed, not a page to consume the token) — mirrors the equivalent page already working in `portal/src/views/VerifyView.vue`. Additionally, there was no way to actually _request_ a magic link from the main app's UI at all — `MagicLinkView.vue` (confusingly named; despite the filename it's the forgot-password request form, calling `/auth/forgot-password`) was the only email-entry form. Added `MagicLinkRequestView.vue` (`/sign-in-link` route, calls `/auth/magic-link`) and a "Sign in with an email link instead" link on the login screen next to "Forgot your password?" so the flow is reachable.
- **`api/src/lib/config.ts` crashed the `api` container at boot in production** (`FATAL: Invalid environment configuration`, `process.exit(1)`) for `PORTAL_JWT_SECRET`/`PORTAL_FRONTEND_URL` — Docker Compose's `${VAR:-}` syntax always defines the env var (empty string if unset), never omits it, and Zod's `.optional()` combined with a stricter validator (`.url()`, `.min(n)`) only skips validation for a genuinely `undefined` value, not a defined-but-empty string. Fixed with a `z.preprocess` wrapper converting empty string to `undefined` on both fields (STACK.md "config.ts's empty-string env var gotcha").
- **`db/schema/*.ts` and `db/client.ts`/`db/numbering.ts`/`db/seed.ts` used extensionless relative imports** (`from './helpers'` instead of `from './helpers.js'`) — silently tolerated by `tsx`'s bundler-style dev resolution and by Vitest/Vite, but a hard crash (`ERR_MODULE_NOT_FOUND`) under plain Node ESM, i.e. any real production run of the compiled output. Found while building the production Docker images above; fixed across all 25 affected files.
- **`PoDetailView.vue`'s cancel-dialog `@hide` handler** had two statements on separate lines with no semicolon between them — tolerated by Vite's dev-mode lazy transform but rejected by a full `vite build`. The first attempted fix never actually landed in a commit; refactored to a named `resetCancelDialog()` method instead of an inline multi-statement expression so it can't silently regress the same way again.

- **Local dev containers for api/worker/web** (STACK.md "Infrastructure" §): `docker-compose.yml` gains `api`, `worker`, and `web` services running the same dev commands as `pnpm run dev`, for verifying the app runs correctly inside a container. New `api/Dockerfile` (shared by `api`/`worker`) and `web/Dockerfile`; new root `.dockerignore`. Fixed the `clamav` service's stale image tag (`1.4-stable` → `1.5.3`, the old tag no longer exists upstream) along the way.

- **Phase 33c — Custom fields (UPGRADE.md G-13/F-24):** generic typed key-value fields per document type, shown on PDFs — see ARCHITECTURE.md §4.15. Completes Phase 33's parity work.
