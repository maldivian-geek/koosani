## Decisions at a glance

## Shared package

A workspace package (`/shared`) used by both api and web. Contains:

- Zod schemas for all request/response shapes
- TS types derived from those schemas (`z.infer`)
- Pure functions for money/tax/date logic that must behave identically on both sides

No runtime dependencies except `zod` and `decimal.js`. Never import Vue, Hono, or Drizzle here.

**`exports` points at `./src/*.ts`, not `./dist/*.js`, by default.** This lets `tsx` (api's dev/test runtime) and Vite (web's bundler) run/bundle the raw TypeScript directly with no separate watch step for `shared` — the `tsc -b --force` rebuild documented above exists purely so the TypeScript _type-checker_ sees changes when checking api/web, not because anything executes the compiled output in dev. A production Node process **cannot** execute `.ts` directly, so `package.json` also declares a `"production"` exports condition pointing at `./dist/*.js` — opted into only by `NODE_OPTIONS=--conditions=production` in `api/Dockerfile.prod`'s runtime stage. Dev/test tooling never sets that flag, so this is a no-op for the existing workflow.

## Infrastructure (recommended baseline)

| Concern                | Choice                                                                       |
| ---------------------- | ---------------------------------------------------------------------------- |
| Hosting (api + worker) | Any Node-capable PaaS (Fly.io, Railway) or VPS                               |
| Reverse proxy          | Caddy or nginx (TLS, gzip, X-Real-IP)                                        |
| Database hosting       | Managed Postgres (Neon, Supabase, RDS) — daily backups, PITR                 |
| Redis                  | Managed (Upstash) or self-hosted                                             |
| Object storage         | Cloudflare R2 (cheapest egress) or AWS S3                                    |
| Email                  | Postmark or SES                                                              |
| Secrets                | Platform's secret manager (Doppler, Fly secrets, etc.) — never `.env` in git |

**Local dev containers (optional).** `docker-compose.yml` also defines `api`, `worker`, and `web` services alongside the infra ones (postgres/redis/clamav) — dev-mode containers running the same `tsx watch`/`vite --host` commands as `pnpm run dev`, with `src/` bind-mounted for hot reload. Not the default workflow (`pnpm run dev` on the host is faster to iterate with); useful when you specifically want to verify the app runs the same way inside a container as it will in production. Host ports 3001 (api) / 5180 (web) — chosen to avoid clashing with the host-run dev servers on 3000/5173. `api`/`worker` share one Dockerfile (`api/Dockerfile`); differ only in `command:`. Secrets come from the gitignored `api/.env` via `env_file:`, never hardcoded in the compose file.

**Production containers (`docker-compose.prod.yml`).** Separate from the dev-container setup above — real multi-stage builds (`api/Dockerfile.prod` compiles TS to JS and runs `node dist/*.js`; `web/Dockerfile.prod` runs `vite build` and serves the static bundle via nginx, `web/nginx.conf`, with SPA client-side-routing fallback), no bind mounts, no local `.env` dependency. Built for a Coolify-style compose-based deploy: all domain-dependent values and secrets are `${VAR}` placeholders, set via the host's env — see the comment block at the top of `docker-compose.prod.yml` for the full required-variables list. `FILES_STORAGE` defaults to `s3` in this file (overridable to `local` as a stopgap) — `api/src/lib/storage.ts`'s local backend is explicitly dev/test-only (its "signed URLs" are fake `local://` strings, not real download links), so production always needs real S3-compatible credentials (`S3_BUCKET`/`AWS_REGION`/`AWS_ACCESS_KEY_ID`/`AWS_SECRET_ACCESS_KEY`, plus `AWS_ENDPOINT_URL` for a non-AWS provider like Cloudflare R2) for uploads/downloads to actually work.

**Postgres is a separate Coolify Database resource in production, not a compose service.** Unlike local dev (`docker-compose.yml`'s `postgres` service, embedded, `postgres:18-alpine`), `docker-compose.prod.yml` has no `postgres` service at all — it's a standalone Coolify-managed `postgres:18-alpine` "Database" resource, created in the same Coolify project/environment as the app but as its own resource. Modeled directly on the same pattern already used by another Maldivian Geek project (`roanuedhuru_v3`) on the same Coolify instance. Reached over Coolify's own shared `coolify` Docker network (`networks: coolify: external: true` in the compose file — Coolify creates and manages this network itself, standalone resources land on it automatically), using the database resource's **UUID as its hostname** (`DB_HOST` env var) — confirmed empirically against the reference project's live config, not just inferred from Coolify's docs. Only `migrate`/`api`/`worker` join this network (they're the only services that talk to Postgres); `redis`/`clamav`/`web` stay on the compose file's implicit default network only. Trade-off: gains a Coolify-managed backup/restore UI and direct per-resource logs/terminal access (no more picking through a multi-container compose app's service selector just to reach Postgres — see the note in the reference-coolify memory file about that selector); loses the simplicity of one fully self-contained compose stack, and depends on Coolify's shared network actually being reliable (unverified beyond this one working reference case at the time of writing).

**`sslmode=prefer`, not `require` — a hard-won lesson.** The first real deploy against the separate Postgres resource above went down: `DATABASE_URL` hardcoded `?sslmode=require`, but the resource's own Coolify metadata reports `"enable_ssl": false` — the actual Postgres server was never configured to accept SSL connections at all, so every connection attempt failed outright. `migrate` exited 1, `api`/`worker` never started (`depends_on: migrate: condition: service_completed_successfully`), and the site went down (Traefik: "no available server") until this was caught and fixed. Now `sslmode=prefer`: attempts an encrypted connection first, falls back to plaintext only if the server doesn't support SSL, rather than treating it as mandatory. If the database resource is ever reconfigured to actually support SSL, this can safely go back to `require`.

**Build/runtime resource caps — a hard-won lesson.** A production build on a shared Coolify host (running other unrelated apps) once spiked memory/CPU hard enough to take the _entire server_ down (the Linux OOM-killer doesn't only kill the offending process — it can take out sshd, dockerd, or unrelated containers too). Both Dockerfiles now cap the build stage's Node heap (`NODE_OPTIONS=--max-old-space-size=768`) and pnpm's install concurrency (`--network-concurrency=4`); `docker-compose.prod.yml` caps every runtime service's memory via `deploy.resources.limits.memory`. `cpu-features` (a native, CPU-heavy accelerator for `ssh2`, itself only pulled in by the `@testcontainers/postgresql` devDependency — never used at runtime) is blocked from building at all via `pnpm-workspace.yaml`'s `allowBuilds`. None of this is a substitute for the host actually having enough RAM/swap for concurrent builds — if this keeps happening, that's the next thing to check.

**pnpm version pinning.** Root `package.json` sets `"packageManager": "pnpm@11.4.0"`; both prod Dockerfiles use `corepack prepare pnpm@11.4.0 --activate` (matching this) rather than plain `corepack enable`. The latter lazily resolves whatever pnpm version corepack picks at first invocation — for `api/Dockerfile.prod`'s runtime stage specifically, that meant a network fetch of pnpm on the container's first cold start in production, which is both fragile (no network access assumed necessary at container runtime) and unpinned/unreproducible build-to-build. `corepack prepare --activate` resolves and caches the exact version inside the build layer instead.

**Migrations + admin bootstrap: a dedicated one-shot `migrate` service in production, the `api` entrypoint in local dev.** `api/docker-entrypoint.sh` is still `api`'s `ENTRYPOINT` in `api/Dockerfile.prod` (and the only one used by local dev's `docker-compose.yml`, unchanged): with no command override, it runs `drizzle-kit migrate` then `api/src/db/seedProd.ts` (compiled to `dist/db/seedProd.js`) before `exec`-ing the actual server, both idempotent, safe on every restart. But `docker-compose.prod.yml`'s `api` and `worker` services both now override the container command (`node dist/server.js` / `node dist/worker.js`) — which makes the entrypoint script skip straight to `exec`-ing that command (`$# -ne 0` check), bypassing migrate/seed entirely for both. Instead, a dedicated `migrate` service (same image, `command: ["sh", "-c", "pnpm exec drizzle-kit migrate && node dist/db/seedProd.js"]`, `restart: "no"`) runs once per deploy and exits; `api`/`worker` both wait for it via `depends_on: migrate: condition: service_completed_successfully`. Modeled on `roanuedhuru_v3`'s `docker-compose.coolify.yml` migrate service — cleaner than every long-running service re-running migrate/seed on its own restarts, and it sidesteps needing a `depends_on: condition: service_healthy` wait on Postgres itself, since the separate database resource is already running continuously rather than starting fresh alongside the app on each deploy.

`seedProd.ts` is the **production-safe counterpart to `seed.ts`** (the dev/demo seed — fixed "Demo Business Pvt Ltd", fixed `admin@demo.mv`/`Admin1234!`, never meant to touch a real database). `seedProd.ts` reads `ADMIN_BUSINESS_NAME`/`ADMIN_EMAIL`/`ADMIN_NAME` from env (required — the entrypoint throws if unset on a genuinely empty database) and either uses `ADMIN_PASSWORD` from env or generates a secure random one, printed once to the `api` container's logs (`docker logs`) and nowhere else. It no-ops immediately if any `businesses` row already exists, so it's safe to leave wired into every container start rather than needing a separate one-time invocation.

**Exposing the api under the web app's own domain: nginx reverse-proxy, not Traefik path routing.** `web/nginx.conf`'s `location /api/` block reverse-proxies to `http://api:3000` on the compose network, stripping the `/api/` prefix before forwarding (the api's own routes are mounted at root — `/customers`, not `/api/customers`). `docker-compose.prod.yml`'s `api` service has **no** `docker_compose_domains`/Traefik routing of its own at all — only `web` is Traefik-routed, to the whole domain. This is a fallback from a first attempt at the same goal purely via Traefik: Coolify auto-generates a `Host && PathPrefix(/api)` router for `api` and `Host && PathPrefix(/)` for `web`, neither with an explicit priority; forcing `api`'s priority explicitly (a real, working label — verified present in the live deployed config) still didn't make Traefik prefer it over `web`'s catch-all in practice, for reasons not fully diagnosable from the Coolify API alone. Routing everything through one Traefik router (`web`) sidesteps the ambiguity entirely — nginx handles the internal split instead. Two nginx gotchas worth knowing if this file is touched again: (1) `resolver 127.0.0.11 valid=10s;` plus a _variable_ `proxy_pass` target is required for nginx to resolve `api` at request time rather than at config-load time — without it, nginx refuses to start at all if `api` isn't yet network-attached the instant this container boots (`depends_on` only guarantees container _start_ order, not DNS readiness); (2) a _variable_ `proxy_pass` target does **not** auto-strip the location's matched prefix the way a literal one does — an explicit `rewrite ^/api/(.*)$ /$1 break;` does that instead, and it must come _after_ the `set $api_upstream ...` line, since `break` halts all further rewrite-module directive processing in the block (a `set` after it never runs).

**`api/src/lib/config.ts`'s empty-string env var gotcha.** Docker Compose's `${VAR:-}` interpolation syntax always _defines_ the container env var (as an empty string if the underlying value is unset), never omits it. A Zod field combining `.optional()` with a stricter validator (`.url()`, `.min(n)`) only skips validation for a genuinely `undefined` value — an empty string is defined-but-invalid, so it fails validation instead of being treated as "not provided." This crashed the `api` container at boot in production (`FATAL: Invalid environment configuration`, `process.exit(1)`) for `PORTAL_JWT_SECRET`/`PORTAL_FRONTEND_URL` specifically (the only two optional fields with a stricter-than-`z.string()` validator) even though the equivalent local `docker run` test never hit it — that test simply never passed those env vars at all, so they were genuinely `undefined`, not empty-string. Fixed with a `z.preprocess(emptyToUndefined, ...)` wrapper on both fields; any _new_ optional env var with a stricter validator needs the same treatment.

## Open decisions (flag and pick before Phase 2)

1. **~~PDF generator~~ — decided Phase 23.** `@react-pdf/renderer` (was recommended, is now installed). Templates live in `api/src/lib/pdf/` (`InvoiceDocument`, `PoDocument`, `SoaDocument` — shared by customer and supplier statements). Rendered via the `pdf` BullMQ queue (worker isolates the CPU cost, per ARCHITECTURE.md §8); routes enqueue and synchronously await completion via `lib/pdfClient.ts`'s `renderAndWaitForFile` (20s timeout) so the documented `GET .../pdf → signed URL` contract holds without the client having to poll a job id.
2. **~~Virus scanning~~ — decided Phase 20.** Self-hosted ClamAV sidecar (`clamd`), spoken directly over TCP via `api/src/lib/virusScan.ts` — no client library needed. `docker-compose.yml` runs it locally; deploy the same image alongside the API in production.
3. **MaxMind GeoLite2** for IP→country (per SECURITY.md). Free with attribution; needs license key.
4. **~~Background OCR~~ — `tesseract.js` added Phase 36, but for order-list image import, not scanned SOAs.** The original question here (scanned supplier PDFs `pdf-parse` can't read) is still open — Phase 36 only wired OCR up for the order-list "import from image" path (ARCHITECTURE.md §4.16): a photo/screenshot of an order table → `lib/ocr-engine.ts` (tesseract.js) → `lib/order-list-ocr.ts` (word clustering) → the existing `order-list-import.ts` parser. Extending OCR to scanned supplier SOAs, if that's ever needed, can now reuse `ocr-engine.ts`'s worker rather than adding a second tesseract.js integration.
5. **FX rate data provider — not decided (Phase 30).** Exchange rates (ARCHITECTURE.md §4.10) are manual entry only in this phase; `exchange_rates.source` is `'manual'` for every row today, but the column exists as an extension point for an automated daily-rate job. No vendor has been chosen or integrated — mirror the `GEO_PROVIDER` pattern (an env-configured provider enum, `disabled` as the safe default) if/when one is picked, rather than hardcoding a single vendor's API.

## Change protocol

Adding or removing any package:

1. Update this file (the right table + a one-line reason in the row).
2. Add a `CHANGELOG.md` entry under the next unreleased version.
3. If the change affects how modules are wired (e.g., swapping PDF generator), update `ARCHITECTURE.md` section 8 or 9 accordingly.
